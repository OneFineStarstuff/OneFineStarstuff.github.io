### 2.2 Trust boundaries

Separate model inference, retrieval, tool execution, control-plane administration, evidence storage, key custody, release signing and external reporting. Require authenticated identities for both users and workloads. Apply least privilege and deny-by-default behavior to cross-boundary calls.

Production authorization should bind a decision to the caller, model and version, tool, permitted action, input-data classification, active policy digest, environment, expiry and approval record. A kill-switch should stop or contain the defined workload through a tested authority path. Its availability, authorization, observed effect, failure mode and recovery process must be tested; the mere existence of a dashboard button or smart contract is not evidence that containment works.

## 5. AI safety and high-assurance RAG

### 5.1 RAG evidence lifecycle

1. **Ingest:** authenticate sources, classify sensitivity, capture source URI/owner/version, retrieval time, access permissions, transformation steps and document digest.
2. **Index:** record embedding/model version, chunking policy, index version and deletion propagation policy. Prevent cross-tenant indexing and access-control leakage.
3. **Retrieve:** enforce access controls before retrieval, use source freshness and trust-ranking rules, and preserve source references for audit.
4. **Compose:** treat retrieved documents as untrusted input. Separate instructions from evidence; detect prompt injection; do not allow documents to grant tools or privileges.
5. **Generate:** require grounded answers, structured outputs where suitable, claim-to-source support and abstention when evidence is insufficient.
6. **Act:** route tools through an authorization gateway with schema validation, allowlists, timeouts, resource ceilings and explicit approval for consequential actions.
7. **Verify:** validate citations, factual support, data leakage, policy compliance, refusal behavior and side effects.
8. **Learn:** store reviewed failure examples with privacy controls, provenance and removal capability. Do not automatically train or change policies from unreviewed user feedback.

The retrieval pipeline should evaluate recall at k, precision at k, citation correctness, unsupported-claim rate, answer completeness, freshness, tenant isolation, refusal accuracy and retrieval poisoning resilience. Safety evaluation must cover malicious content inside source documents and conflicts between a retrieved source and a higher-priority policy.

### 5.2 Alignment, robustness, interpretability and adversarial evaluation

Establish a lifecycle evaluation plan covering capability and hazard identification, instruction hierarchy integrity, prompt injection and tool misuse, harmful output boundaries, data exfiltration, adversarial robustness, model uncertainty, distribution shift, interpretability where available, human factors, and safe shutdown or rollback.

For advanced-agent and AGI/ASI-related scenarios, maintain a threat model and staged capability gate rather than pretending a universal containment proof exists. Test bounded authority, resource limits, least-privilege tools, independent monitoring, circuit-breaker behavior, deception-sensitive evaluations where justified, cross-agent coordination failure and recovery from
corrupted memory or retrieved evidence. Results must describe test coverage and limitations; they cannot prove that every future behavior has been ruled out.

An independent reviewer should approve release criteria for high-impact workflows. Separate developer-run tests, independent validation and formal risk acceptance. Release should be blocked if a severe unmitigated hazard, unbounded tool permission, unverifiable model provenance or failed containment test remains.

## 8. PQC, WORM, Merkle-DAG and evidence continuity

### 8.1 Standards mapping

- **NIST FIPS 203 / ML-KEM:** key encapsulation; it is not a digital-signature algorithm.
- **NIST FIPS 204 / ML-DSA:** digital signatures. ML-DSA-65 and ML-DSA-87 are parameter sets in this family; the family derives from CRYSTALS-Dilithium.
- **NIST FIPS 205 / SLH-DSA:** stateless hash-based digital signatures, based on SPHINCS+.
- **Falcon-1024:** do not describe it as standardized by FIPS 203, 204 or 205. If considered for a project profile, mark it as a separate algorithm choice and obtain cryptographic and procurement review before production use.

The cryptographic inventory should name exact algorithm identifiers, parameter set, implementation/build digest, validation status, key identifier, purpose, custody boundary, rotation event and revocation path. A policy should distinguish signature algorithms from KEMs, transport encryption, symmetric message authentication and digest algorithms.

## 13. OpenAI Platform and enterprise integration pattern

Use a server-side service adapter for model calls and tool orchestration. Never put API keys, privileged credentials, signing keys or unrestricted tool access in client-side application code.

The adapter should:
- select models through a versioned configuration and fallback policy;
- maintain prompt/system-instruction version identifiers;
- validate structured outputs against schemas;
- mediate tools using server-side allowlists, authorization checks and bounded capabilities;
- log request correlation IDs, policy and model versions, usage and error metadata without unnecessarily retaining sensitive payloads;
- support privacy and retention decisions, including disabling storage where required by the application design;
- run golden-set and adversarial evaluations before model or prompt upgrades;
- compare quality, safety, latency, cost and failure modes before traffic promotion;
- offer a kill path for a model, tool or workflow and preserve incident evidence.

The platform integration must be treated as one component in the larger assurance chain. It does not replace the organization’s own RAG access controls, security review, application-level authorization, legal analysis, incident-response plan or supervisory obligations.
