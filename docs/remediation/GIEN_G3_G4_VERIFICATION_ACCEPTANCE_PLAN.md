## G3 — TPM / TEE hardware attestation acceptance

### 1. Trust and evidence model

A successful G3 result must be generated by a verifier operating on signed, fresh and attributable evidence. PCR equality alone is insufficient.

The target pipeline is:

1. **Enrollment and identity:** identify the device or virtual platform and its endorsement identity. Validate the Endorsement Key (EK) certificate, or an approved enrollment binding, against configured manufacturer or enterprise trust anchors.

Establish the Attestation Key (AK) public-key identity and its authorized binding to that platform. Check certificate validity, policy constraints and revocation status under the selected trust program.
2. **Verifier challenge:** generate a cryptographically random, one-use nonce (minimum 256 bits for this design), bind it to the device identity, requested PCR bank/indices, appraisal policy version and a short expiry, then store it in a replay-protected challenge registry.
3. **Quote acquisition:** request a TPM 2.0 quote over the exact PCR selection. The signed attestation structure must include the outstanding verifier nonce in the quote's qualifying data / extraData field.
4. **Quote validation:** parse the TPM 2.0 attestation structure using a conformant TPM implementation. Check the TPM-generated magic/type fields, signer identity, selected PCR bank/indices, nonce equality, signature algorithm and signature under the enrolled AK.

Check quote clock/reset/restart information and freshness policy. Reject an absent, expired, previously consumed or mismatched challenge.
5. **Event-log appraisal:** obtain the event log for the quoted measurement point. Replay the log by applying each event's digest to its selected PCR using the correct bank algorithm and TPM extend semantics.

Reconstruct the selected PCR values/digest and compare them with the quote. Independently classify each event against signed, versioned reference values and appraisal policy. Reject an event log that cannot reconstruct the signed quote.
6. **TEE appraisal:** handle Intel TDX, AMD SEV-SNP, ARM CCA or another TEE only through a named, versioned vendor-specific evidence verifier and trust policy. A TPM PCR verifier is not a generic TEE report verifier.
7. **Decision and receipt:** emit a structured, immutable decision record containing platform identity, quote and event-log hashes, selected PCRs, policy/reference-value version, challenge ID, verification time, verifier implementation/version, trust-anchor IDs, decision state and failure codes. Record a successful result only after every required check passes.

### 2. Required verifier interfaces

The implementation should keep cryptographic parsing, trust validation, event-log replay and policy appraisal independently testable. Exact types must be chosen with the selected TPM/TSS/vendor implementation; do not invent a generic byte-equality API that can be mistaken for a hardware quote.

Minimum conceptual interfaces:

- `ChallengeStore`: issue, retrieve and atomically consume a nonce bound to platform, PCR selection, policy version and expiry.
- `PlatformIdentityVerifier`: validate EK/AK enrollment and certificate/trust chain against explicit trust anchors and revocation policy.
- `TPMQuoteVerifier`: parse and verify TPM 2.0 quote signature, attestation type, nonce, PCR selection/digest and clock information.
- `EventLogReplayer`: replay the supported TCG event-log profile and reconstruct the PCR values selected by the quote.
- `ReferenceValueAppraiser`: compare measurements and event records against signed, versioned baseline policies.
- `TEEQuoteVerifier`: separate provider-specific verifiers for each explicitly supported TEE evidence format.
- `EvidenceReceiptWriter`: persist the decision and associated evidence hashes to the approved immutable evidence store only after the independent storage controls are available.

### 3. Fail-closed states

The default decision must be `UNVERIFIED`. Do not default to `PCR_MATCH=TRUE`.

Use an explicit vocabulary:

| State | Meaning |
|---|---|
| `VERIFIED` | Quote signature, enrolled AK identity, nonce, PCR selection/digest, event log and reference policy all passed. |
| `REJECTED` | Evidence was evaluated and one or more integrity/policy checks failed. |
| `STALE` | Nonce, quote clock, certificate or evidence freshness requirement failed. |
| `INCOMPLETE` | Required quote, event log, certificate or policy artifact is missing. |
| `UNSUPPORTED` | Evidence format, PCR bank, TEE provider or algorithm is outside the explicitly approved support profile. |
| `UNVERIFIED` | No complete verification decision has been made. |

A missing verifier, missing trust root, unavailable reference-value store, timeout, parser error or unrecognized evidence type must never become a successful decision.

### 4. G3 negative and positive test matrix

Required tests before a hardware-attestation claim may be considered:

- Valid enrolled AK + valid TPM quote + outstanding nonce + selected PCR digest + replay-consistent event log + approved references: accepted by a real-provider integration test.
- Modified quote bytes or signature: rejected.
- AK certificate not rooted in configured trust anchors, revoked certificate, or AK/platform binding mismatch: rejected.
- Wrong, expired, consumed or repeated nonce: rejected.
- PCR bank or selection mismatch: rejected.
- Quote digest inconsistent with PCR values or event-log replay: rejected.
- Unknown event, unsupported bank/algorithm, truncated or malformed event log: rejected or unsupported, never accepted.
- Stale quote clock, unacceptable reset/restart counter change, or firmware/policy version outside the approved range: rejected.
- Golden/reference baseline signature invalid, expired or unavailable: unverified/rejected.
- Missing event log where appraisal policy requires it: incomplete.
- Provider timeout or partial response: unverified with a recoverable error code.
- Vendor TEE report: positive and negative tests for each named provider; never route it through the TPM PCR-only path.

Mock tests may verify orchestration and failure-state handling, but only provider-backed integration tests against actual supported hardware or a documented vendor attestation test environment can provide evidence of real quote verification.

### 5. G3 prerequisites still requiring owner selection

Before implementing a provider-backed verifier, the system owner must identify:

- Supported TPM version/profile, manufacturer and platform classes.
- TSS/API and OS/device access path.
- Endorsement/AK enrollment process, manufacturer trust anchors, certificate profiles, revocation source and key-rotation policy.
- Supported event-log profile(s), PCR banks, PCR selection and baseline/reference-value lifecycle.
- Freshness limits, nonce store, replay prevention and clock/counter policy.
- TEE vendors and exact quote/evidence formats, if any.
- Data classification, evidence retention, privacy and operational responsibilities.
- Independent reviewer and real-device acceptance environment.

Until those are supplied, G3 remains DESIGN ONLY / NO HARDWARE ATTESTATION.

## G4 — executable SIP v3.0 formal verification acceptance

### 1. Model structure

Replace the current comment-only PlusCal sketch with an executable TLA+ module that explicitly declares:

- Finite model constants and assumptions: institutions, root set, messages, quorum threshold, epoch and bounded fault variables.
- State variables for each institution's attestation/log state, message delivery, root proposals, prepare/commit votes, committed STHs, protocol epoch and network/decision state.
- `Init`: a valid initial state with defined domains for every variable.
- `Next`: the disjunction of explicit transition actions (issue/relay attestation, message loss/duplication/reordering where modeled, prepare, vote, authorize commit, commit, timeout/recovery and divergence handling).
- `Spec == Init /\\ [][Next]_vars`, plus fairness assumptions only where the liveness claim requires them.

The model must state which behavior is abstracted. For example, a finite model may represent STH hashes as symbolic finite values and treat cryptographic hash/signature correctness as assumptions; that is not a cryptographic proof.

### 2. Required safety properties

At minimum, model and check:

- `TypeOK`: every state variable remains within its declared finite domain.
- `NoCommitWithoutQuorum`: a root cannot commit a new STH before the specified quorum/authorization condition.
- `CommittedRootAgreement`: all roots that have committed the same epoch agree on the committed STH value.
- `NoSilentDivergence`: distinct committed views cannot remain unreported by the protocol's divergence state.
- `NoRollback`: a root cannot move to an older committed epoch/STH.
- `SingleDecisionPerEpoch`: one epoch cannot acquire conflicting terminal decisions.
- `EvidenceBinding`: a committed STH corresponds to the same prepared proposal and evidence set that passed the modelled authorization guard.

Use explicit temporal properties for liveness. State the fairness and synchrony assumptions needed; do not claim eventual convergence under permanent message loss, a permanently unavailable quorum or an unfair scheduler.

### 3. Required counterexample and mutation tests

A successful-only run is insufficient. Include intentional mutant variants or parameterized negative configurations that demonstrate TLC detects:

- Commit before quorum.
- Different roots committing different proposals.
- A proposal changing after the prepare/authorization boundary.
- A lost prepare/commit message preventing liveness under the declared assumptions.
- A replayed or stale epoch being accepted.
- A divergence state that is not surfaced.

The negative fixtures must fail for the intended invariant/property. Their counterexample traces must be retained as test artifacts.

### 4. Reproducible TLC evidence bundle

For each checked model/configuration, preserve:

- Exact TLA+ source and `.cfg` file hashes.
- TLC/tool distribution version, artifact digest, Java runtime version and command line.
- Model constants, symmetry sets, invariants, temporal properties, constraints and fairness assumptions.
- State count, distinct-state count, transition count, depth/diameter and completion status.
- Full stdout/stderr and any counterexample traces.
- Machine-readable result JSON tied to the source/config/tool hashes.
- CI run ID and artifact digest.
- Independent review of modelling assumptions, state abstraction and claimed properties.

A report with a placeholder date, no config/tool version or no reproducible trace is not accepted as formal-verification evidence. A finite-state model-checking result must be described as model checking within the stated model bounds and assumptions, not as proof of the deployed distributed system.

### 5. G4 implementation sequence

1. Freeze the protocol invariants and safety/liveness claims with an accountable reviewer.
2. Create an executable pure TLA+ state machine and minimal finite model configuration.
3. Run TLC locally/CI, fix syntax errors and counterexamples, then add mutant/negative models.
4. Pin the TLC distribution and Java runtime in GitHub Actions; verify downloaded artifacts before execution.
5. Upload logs, traces, config, source hashes and machine-readable results as immutable CI artifacts.
6. Replace the old “Final” report with a dated, evidence-linked report showing exact model scope and assumptions.
7. Require independent formal-methods review before describing the SIP model as verified.

Until a reproducible TLC run and independent review exist, G4 remains DESIGN ONLY / NO FORMAL ASSURANCE.
